# Перенос ядра физики на Rust — эксперимент

Ветка `alpha-0.2.4-rust-physics`, папка `.claude/worktrees/rust-physics`. Начат 20.11.2026.
База — последний коммит ветки `alpha-0.2.4-perf-experiment` (`75a0c2b`, 11.11). Незакоммиченная
работа из рабочей копии perf-experiment (каталог стендов, эталонный решатель, клин, гашение) сюда
НЕ входит: её коммита нет.

## Задача пользователя (20.11)
Переписать ядро физики на Rust, чтобы понять, сколько даёт Rust по скорости. JNI — как можно
меньше вызовов за тик. Rust проверять тестами Kotlin, на каждом этапе — тесты и стенды. Идеал —
полный детерминизм между Kotlin и Rust и выигрыш больше чем в 2 раза. Замеры скорости — только
после отмашки пользователя, на ПК и на старом Samsung.

## Решение о дальнейшем (20.11, после замеров)
Слова пользователя: сначала дооптимизировать и дочинить физику на Kotlin, потом сделать полную
версию на Rust. Дальше вести обе параллельно: Kotlin — эталон и основная реализация, Rust —
только там, где даёт реальный прирост (например, Android). Многопоточность в Rust пока не делается.

Что из этого следует для переноса (выводы, не слова пользователя):
- Побитовое совпадение Kotlin ↔ Rust — обязательное условие: `.bug`, записанный на телефоне с
  Rust, должен повторяться на ПК с Kotlin. Пока Rust в ходу, тесты сверки и тень (`-PrustShadow`,
  в т. ч. `:lwjgl3:bugReplayCheck`) — постоянная часть проверок.
- База этого переноса — `75a0c2b`. Позже `git diff 75a0c2b..<новый коммит> -- physics/` покажет
  ровно то, что переносить, а тень — где Rust отстал. Править Kotlin сейчас можно свободно; дешевле
  перенос будет, если физика по-прежнему меняется только через методы `PhysicsWorld` и из
  математики берёт `+ - * /`, `sqrt` и `StrictMath.sin/cos/acos` (для других функций StrictMath
  понадобится перенос fdlibm в `jmath.rs`).
- «Реальный прирост на Android» мерить против настоящей настройки игры: там Kotlin считает с
  воркерами, а Rust пока в один поток. Ещё нужен режим «физика целиком на Rust» (п. 6 статуса).

## Устройство
- `physics-native/` — workspace Cargo: `core` (крейт `genomeia-physics`, чистый Rust без JNI,
  `cargo test`/clippy) и `jni` (cdylib `genomeia_physics_jni`, единственное место с unsafe JVM).
- Kotlin: `physics/.../physics/rust/RustPhysics.kt` (загрузка, внешние функции),
  `RustWorld.kt` (мир на Rust с методами PhysicsWorld), `RustDigest.kt` (отпечаток состояния),
  `RustShadow.kt` (теневой режим). Gradle: `:physics:cargoBuild`, `:physics:cargoTest`;
  `:physics:test` сам собирает библиотеку и передаёт путь свойством `genomeia.physics.native`.
  Без cargo (или `-PnoRust=1`) тесты Rust пропускаются.
- Rust ставится в `%USERPROFILE%\.cargo` (rustup, PATH не трогали); Gradle находит cargo сам.
- Дословный перенос: тот же порядок операций с плавающей точкой, те же типы (float/double),
  тот же обход. `jmath.rs` — Math.min/max по коду JDK (NaN, ±0), fdlibm sin/cos/acos как
  StrictMath (сверка на миллионе аргументов — `RustSmokeTest`). FMA нет.
- Kotlin держит общие ссылки на массивы из нескольких объектов; в Rust у каждого массива один
  хозяин (BodyState), остальные получают его параметром. Списки контура/изгиба/лоскутов после
  сборки — прямо из `local_boundary` (в Kotlin это ссылки после syncBoundaryArrays).
- Перенесён ПОСЛЕДОВАТЕЛЬНЫЙ путь каждой стадии. Параллельные пути Kotlin по построению дают
  те же биты; это проверено и здесь: тень сверяет Kotlin на 2/4/7/8 воркерах с последовательным
  Rust (см. ниже). Воркеры в Rust — этап 4.
- Граница JNI: `worldStep` — один вызов на тик. Правки между тиками — `worldCall(op, …)`
  (коды — функция `call` в `jni/src/lib.rs` и `RustWorld.kt`).

## Сверка
- `RustDigest` и `digest.rs` пишут один и тот же отпечаток состояния: 44 именованных раздела
  (частицы, связи, треугольники, топология, контур, поверхность, сон, организмы, пределы, блоки,
  касания, журналы гибели, счётчики). Расхождение печатается разделом и первым разным байтом.
- Тесты `physics/src/test/.../rust/`: `RustParityTest` (7 сцен без касаний),
  `RustContactParityTest` (5: касание, таран 2.5/5/9 клеток за тик с CCD, пробоем и гибелью,
  складка мышцей, удар по спящему, без гибели и без касаний), `RustWorldOpsParityTest` (5:
  дописывание тел, рост из зиготы, свободные частицы и стенка, удаление тела и уплотнение, снимок
  в обе стороны — байты снимков Kotlin и Rust равны и читаются накрест), `RustSmokeTest` (3).
  Каждая сцена проверяет и то, что явление случилось, и что сверка ловит подмену одного бита.

## Теневой режим — проверка на любых стендах, проверках и в игре
`-PrustShadow` (Gradle, для любого JavaExec и Test) или `-Dgenomeia.physics.rust=shadow`: каждый
`PhysicsWorld` заводит рядом мир на Rust, повторяет в нём все свои методы (загрузка, тела, рост,
пул частиц, мышцы, тяга, связи, снимок и т. д.) и ПОСЛЕ КАЖДОГО ТИКА сравнивает отпечатки
побитово. Первое расхождение — исключение с тиком и разделом. В конце прогона в stderr:
`тень Rust: миров N, сверено тиков M …` — зелёный прогон без этой строки значит, что тени не было.
- Параметры, которые стенды крутят прямо в BodyState (мышцы, cancelSpinOn, contactsOn, флаг сна,
  мышь, номер тика…), переносятся в тень перед каждым тиком (`RustWorld.syncParams`).
- Правки стенда в обход методов мира (Probe, сцены столкновений пишут позиции, скорости, массы
  прямо в массивы): перед тиком миры сравниваются по разделам; если расходятся только плоские
  данные (px…matchWeight, мышцы, течение среды, служебные счётчики, пометки порванных связей
  conDead, флаги вывернутых треугольников, которые пишет диагностика окна), они переносятся в Rust и
  считаются в итоге («перенесено правок стенда K (разделы …)»). Расхождение в структуре — остановка.
  Лазейка: неверная операция мира между тиками в тех же плоских разделах тоже была бы
  «перенесена». Её закрывает `-Dgenomeia.physics.rust.checkOps=true` — строгая сверка после
  КАЖДОЙ операции мира (перенос — только до неё).
- `-Dgenomeia.physics.rust.every=N` — сверка раз в N тиков; `…rust.adopt=false` — без переноса.
- Сама тень проверена тестом `RustShadowTest`: идёт за миром через методы и сверяет каждый тик,
  плоскую правку стенда переносит ровно один раз, правку структуры (длина покоя связи)
  останавливает, в строгом режиме останавливает любую правку.
- Тень не меняет мир Kotlin: вывод стендов с тенью и без неё совпадает байт в байт (проверено на
  всех падающих стендах ниже).

## Замер скорости в один поток — ПК (20.11, по отмашке пользователя)
Стенд `gradlew :physics-lab:rustSpeedBench -Pcells=100000 -Pwarm=150 -Pmeasure=150 -Pblock=10`
(`RustSpeedBench.kt`). Сцена — толпа crowdBench (`CrowdScene`, сцену вынес из CrowdBench; его
CROWD_HASH до и после выноса тот же, `5e785443ee4139a8` на 5000 клеток). Мир Kotlin без воркеров
и мир Rust шагают ШАГ В ШАГ блоками по 10 тиков, порядок в паре блоков чередуется: дрейф частоты
и нагрев ложатся на обоих поровну. После каждой пары блоков позиции и скорости сверяются
побитово, до первого тика, после прогрева и в конце — полный отпечаток. В таймере только шаг
(у Rust — вместе с вызовом JNI), толчок и сверки — вне его.
Машина: AMD Ryzen 7 5700G (8 ядер / 16 потоков, L2 4 МБ, L3 16 МБ), 64 ГБ, Windows 11; Liberica
JDK 21.0.7 (HotSpot C2), `-Xmx3g`, участок G1 32 МБ; Rust 1.100 release (LTO fat,
codegen-units 1, opt-level 3). Прогрев 150 тиков, замер 150; 6 подшагов.

Во всех прогонах сверка сошлась (30 сверок частиц, 3 полных отпечатка), CROWD_HASH тот же, что у
crowdBench (`3c011b6f45407382` — 20k, `0504f37cc246cea7` — 100k). Сборка под AVX2:

Выводы:
- Дословный перенос в один поток на ПК быстрее Kotlin на 4–8%, а не в 2 раза. Время самого Rust
  от сборки почти не зависит (10.75 → 10.54 мс, 74.8 → 75.1 мс); отношение ×1.04 или ×1.08
  определяет разброс Kotlin между запусками (11.35 и 11.80 мс, 77.8 и 81.3 мс): JIT в каждом
  запуске компилирует немного по-своему.
- AVX2 Rust не ускоряет. Видимо, код упирается в память (обращения к частицам по номерам из
  связей и касаний), а не в арифметику; профилем это не проверено. Биты с AVX2 те же: FMA сам
  Rust не подставляет.
- Почему так мало: перенос дословный — те же массивы, тот же обход, тот же порядок операций, а
  именно такой код HotSpot C2 после прогрева компилирует не хуже LLVM. Rust обгоняет JIT там, где
  делает то, чего JIT не может (явный SIMD, своя раскладка данных, циклы без проверок границ); но
  раскладка и float меняют биты или так же доступны Kotlin.
- У Rust ровнее худшие тики: максимум 14.4 против 21.0 мс (20k), 95.6 против 103.7 мс (100k).
  Вероятная причина выбросов Kotlin — сборка мусора и перекомпиляции JIT (не проверено).
- Телефон — следующий раздел. Время до прогрева JIT в замер не входило.

Выводы:
- На телефоне дословный перенос быстрее Kotlin в 2.3 раза при полном побитовом совпадении — то,
  что пользователь назвал идеалом. На ПК — только на 4–8%.

  циклы не хуже LLVM, а код ART на Android 10 на том же процессоре и тех же данных вдвое
  медленнее Rust. Отношение по парам блоков ровное (2.2–2.4): JIT к замеру прогрет.
- Абсолютно, в один поток на этом телефоне: 5k — 15 UPS на Kotlin и 35 UPS на Rust; 20k — 3.5 и
  7.8 UPS.
- Не проверено: Kotlin, скомпилированный заранее (AOT — так его со временем компилирует фоновая
  оптимизация установленного приложения). dex2oat из adb shell закрыт SELinux, нужно тестовое
  приложение. Компилятор там тот же (оптимизирующий компилятор ART), поэтому большой разницы с JIT
  я не жду, но это не замерено. Не мерили и другие телефоны: на больших ядрах (Cortex-A7x)
  отношение может быть другим.
- Ключ `-Xusejit:false` у app_process JIT не выключает: свойства телефона (`-Xusejit:true`)
  дописываются после ключей командной строки. Так что сравнить «JIT против интерпретатора» им нельзя.

## SIMD и разбор времени по стадиям (20.11, по просьбе пользователя «выжать максимум»)
Условие то же: биты Rust = биты Kotlin. Поэтому SIMD здесь только поэлементный — каждая дорожка
делает те же операции IEEE (`+ - * /`, корень, сравнения, выбор по маске) в том же порядке, без FMA
и без сумм по дорожкам.

Что сделано:
- `core/src/stage_timer.rs` — таймеры стадий как у Kotlin (`dbgTimeNs`, те же 21 номер и
  границы); стенд с `-Pstages=1` печатает таблицу стадий всех миров рядом.
- `core/src/simd.rs` — две дорожки f64 (`F64x2`): SSE2 на x86_64, NEON на aarch64, пара скаляров
  на прочих. Тесты каждой операции против скалярной на особых значениях (NaN, ±0, ±∞, денормалы).
- СВЯЗИ ДВУХ БЛОКОВ СРАЗУ (`kernels::solve_block_links_pair`, `iteration.rs`): блоки одной чётности
  не делят частиц, их связи перестановочны, поэтому связи блока b и следующего бодрствующего блока
  той же чётности считаются вместе — по дорожке на блок, внутри дорожки порядок прежний. Остальные
  стадии блоков идут в прежнем порядке; интегрирование и связи второго блока переезжают раньше
  хвоста первого — события топологии (разрывы) случаются только в пределах длины, так что их
  порядок и журналы не меняются; блоки `serial_block` в пару не идут. Юнит-тест: пара против двух
  скалярных вызовов на случайных блоках (мёртвые, закреплённые, вырожденные связи, дыры, все ветви
  длины покоя, оба направления) — побитово.
- ПРОХОДЫ ЧАСТИЦ НА СРЕЗАХ И ПО ДВЕ: интегрирование, восстановление скоростей, лёгкий проход,
  проход после касаний (среда, внешний импульс). Срезы вместо `self.px[i]`: через `&mut self`
  компилятор не знает, что запись в один массив не меняет адрес другого, и перечитывает поля.
- `RustWorld.simd` (JNI 142) — переключатель SIMD во время работы: стенд `-Pscalar=1` гоняет
  третий мир «Rust без SIMD» в том же процессе. По умолчанию SIMD включён везде.

Как проверено: юнит-тесты Rust на ПК и на телефоне (тот же тестовый файл, собранный под aarch64 и
запущенный по adb, — ветка NEON на Exynos 850); `:physics:test` (85, падает только прежний
`SoftnessTest`); тень на сборке с SIMD — толпа 100k (Kotlin на 8 воркерах ↔ Rust с парами блоков,
29 540 разрывов) 300 тиков, сумма `0504f37cc246cea7`; collisionBench медуза/кирпич по 17 966;
physicsCheck медуза 11 117 / кирпич 9 275 (их собственные проверки — 5/31 и 1/31, как на базе);
во всех прогонах rustSpeedBench (ПК и телефон, все миры) — побитовая сверка с Kotlin.

ПК (Ryzen 7 5700G), в одном процессе, Kotlin и Rust шаг в шаг:

| Сцена | Kotlin, мс/тик | Rust до SIMD | Rust с SIMD | Rust быстрее Kotlin: до → после |
|---|---|---|---|---|
| 5k | 2.65 | 2.49 | 2.21 | ×1.07 → ×1.20 |
| 20k | 11.24 | 10.54–10.75 | 9.35 | ×1.04–1.06 → ×1.20 |
| 100k | 84.83 | 74.76–75.09 | 75.27 | ×1.04–1.08 → ×1.13 |

Вклад SIMD — три мира в одном процессе (Kotlin, Rust, Rust без SIMD), с таблицей стадий: 20k —
×1.09–1.11 ко всему тику (связи ×1.22, восстановление скоростей ×1.29, интегрирование ×1.15); 100k —
×1.04 (связи ×1.23, проходы частиц +4–7%: при 100k они ждут память). Опыт A/A (два одинаковых
мира Rust, `-Pscalar=2`) на ПК — ×1.00, так что эти числа чистые. При 100k главная стадия — уже
подготовка касаний: 31.7 из 85 мс (37%), SIMD её не касается.

Телефон (Samsung A21s, 8 × Cortex-A55):

| Сцена | Kotlin, мс/тик | Rust до SIMD | Rust с SIMD | Rust быстрее Kotlin |
|---|---|---|---|---|
| 5k | 72.14 | 28.80–28.83 | 28.22 | ×2.56 (до SIMD ×2.29–2.31) |
| 20k | 315.0 / 363.0 (два прогона) | 127.9 | 121.2 / 113.7 | ×2.60 / ×3.19 (до SIMD ×2.26) |

Kotlin на ART гуляет между запусками на 15–25% (5k: 58–72 мс, 20k: 288–363 мс) — JIT каждый раз
компилирует по-своему, — поэтому отношение даю диапазоном; внутри прогона оно ровное (по парам
блоков ×2.56–2.62). Rust стабильнее: при 20k он стал быстрее на 5–11%, при 5k — на 2%.

Вклад SIMD на телефоне — около ×1.03 ко всему тику (интегрирование +17%, восстановление скоростей
+16%, связи +2%). Мерить его пришлось обходным путём:
- ОПЫТ A/A на телефоне показал, что два ОДИНАКОВЫХ мира Rust в одном процессе расходятся на 5–10%,
  а интегрирование и восстановление скоростей — до ×1.6; медленнее всегда первый созданный мир. Не
  очередь: схема Уильямса (каждый мир идёт после каждого одинаково часто) не помогла; не тёплый кэш
  после сверки: вытеснение кэшей проходом по 32 МБ после каждой сверки выровняло прочие стадии
  (×0.96–0.99), но не эти две; не совпадение адресов внутри страницы: распределитель, сдвигающий
  крупные массивы на разные «цвета» по 64 байта в пределах 8 КБ, разрыв не убрал (откачен).
  Похоже на физическое размещение страниц — без счётчиков процессора не разобрать.
- Поэтому вклад SIMD — среднее геометрическое двух прогонов с ролями наоборот (`-Pscalar=1` и
  `-Pscalar=3`): ×0.97 и ×1.09 → ×1.03.
- Почему так мало: у Cortex-A55, насколько я знаю, тракт double узкий, а деление и корень не
  конвейерные — две дорожки NEON считаются почти как две скалярные операции. Пробовал и пару
  связей двумя скалярными цепочками вперемешку (для процессора, исполняющего по порядку): связи
  стали медленнее, 9.1 мс против 7.9 — откачено. На больших ядрах (Cortex-A7x) NEON double
  должен помогать как на ПК, но такого телефона не было.

Стенд: `-Pmeasure=180` при трёх мирах (полный цикл схемы Уильямса — 6 пар блоков); после каждой
сверки — вытеснение кэшей. Сравнивать числа разных запусков нельзя ни на ПК, ни тем более на телефоне.

Что ещё можно сделать (оценки — на сцене толпы, один поток):
1. Воркеры в Rust (этап 5, ~2.3 тыс. строк Kotlin) — единственное, что даст кратный выигрыш на
   телефоне: у A21s 8 ядер. Без них игра на Rust в один поток проиграет многопоточному Kotlin.
2. Подготовка касаний: при 100k на ПК — 37% тика Rust, на телефоне — 14%. Не SIMD, а раскладка
   (частицы по ячейкам сетки подряд) и разбор профилем. Оценка — десятки процентов этой стадии.
3. Площади (11–15% тика): пары независимых треугольников внутри блока по расписанию — биты те же,
   нужно перестраивать расписание при правке списка. Около +2–3% ко всему тику на ПК.
4. AVX2 на ПК — четыре блока связей сразу, с проверкой процессора во время работы: +10–20% стадии
   связей на ПК; телефону не поможет.
5. PGO (сборка по профилю) для Rust: обычно +5–15% на ветвистом коде (касания), биты не меняет.
6. float вместо double — вдвое больше дорожек SIMD и вдвое меньше памяти, но это смена физики
   (биты другие и у Kotlin), решение не про перенос, а про игру.

## План этапа 5 — воркеры в Rust
Что распараллелено в Kotlin (каждое место — свой путь кода, не тот же последовательный цикл):
блоки связей по чётностям с остановкой на событиях топологии и доработкой по порядку
(`ParallelBlocks.solveBlocks/solveSeams`), пределы длины по блокам, ориентация контура и
сопротивление по рёбрам, скорости (до/после/лёгкий проход, `finishTouched`), импульс за тик
(`momentumCancel`: группы, суммы по кускам, слияние), дрожь, среда (`comSums`, `flowPayment`,
вязкость), пластика, мышцы (`ParallelMuscles`: кольца по цветам, сглаживание), касания
(`ParallelContacts`: кандидаты, пары, CCD, сборка, сдвинутые, переразмещение, кости, пробой;
`ParallelContactSolve`). Всего ~2.3 тыс. строк Kotlin.
Как переносить:
- Свой пул потоков, как `SpinPhysicsWorkers`: курсор раздачи и счётчик в разных линиях кэша,
  короткий спин, без аллокаций в тике; число воркеров — из конфигурации мира, не больше ядер.
- Те же куски и тот же порядок слияния, что у Kotlin (`PASS_CHUNK`, блоки, швы, цвета), — тогда
  результат побитово тот же при любом числе воркеров с обеих сторон.
- Общие массивы между потоками — через обёртку с сырым указателем (каждый кусок пишет только свои
  частицы — то же условие, что в Kotlin); счётчики — в слотах воркера с разносом 128 байт.
- Проверка — та же тень: Kotlin на 1/2/4/7/8 воркерах против Rust на 1/2/4/7/8 воркерах.
