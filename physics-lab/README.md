# Лаборатория физики

Окно, файлы, повтор записей, диагностика, проверки и замеры новой физики.
Зависит от `:physics`, `:render` и настольного libGDX. От `:core` и `:lwjgl3`
не зависит. Непосредственное рисование примитивов остаётся в `:render`.

Пакеты внутри `io.github.some_example_name.physics.lab`:

| Пакет | Что искать |
|---|---|
| `session` | Состояние сессии, настройки запуска, применение команд журнала |
| `window` | `RealBodyDemo`, окно, ввод, интерполяция и подготовка рисунка |
| `io` | Чтение body-export и формат `PlayerLog` |
| `scenes` | Сценарии столкновений и генератор мягкой решётки |
| `inspection` | `Probe`, именованный доступ для диагностики, отчёты |
| `replay` | Повтор журнала игрока и старого drag-log |
| `checks` | Физические регрессии, проверка записи, скрытого состояния и окна |
| `bench` | Время тика, масштаб 10k/100k, раскладка памяти и численная точность |
| `tuning` | Подбор мышц и сохранённое независимое зеркало `SwimSolver` |

## Запуск

Окно запускается платформенными обёртками в `lwjgl3/src/lab/kotlin`:

```text
gradlew --no-daemon :lwjgl3:realBodyDemo -Pbody=body-export.txt
gradlew --no-daemon :lwjgl3:realBodyDemo -Pplay=<запись> -Pspeed=4
gradlew --no-daemon :lwjgl3:softGridLab -Pseed=12345
```

У `lwjgl3` это отдельный source set `lab`: лаборатория не входит в classpath
или JAR основной игры. Проверки основной игры находятся в `lwjgl3.verification`.

Безоконные инструменты запускаются прямо из этого модуля:

```text
gradlew :physics-lab:test
gradlew :physics-lab:physicsCheck -Pbody=body-export.txt
gradlew :physics-lab:materialCheck -Pbody=body-export.txt
gradlew :physics-lab:materialCheck --args="body-export.txt --tearing"
gradlew :physics-lab:playerLogSelfTest -Pbody=body-export.txt
gradlew :physics-lab:playerReplay -Plog=<запись>
gradlew :physics-lab:tissueReplayCheck -Plog=<запись>
gradlew :physics-lab:scaleBench -Pbody=<тело> -PscaleScene=all
gradlew :physics-lab:swimTune --args="--pop 64 --gen 60 --seed 7"
```

Старые задачи `:lwjgl3:physicsCheck`, `:lwjgl3:playerReplay` и остальные безоконные
команды оставлены как перенаправления; свойства `-P...` работают как прежде.
Аргументы `--args` задаются у настоящей JavaExec-задачи в `:physics-lab`.
`materialCheck --tearing` дополнительно проверяет, что живой треугольник
не остаётся вывернутым более десяти последовательных тиков при включённом разрушении.

`tissueReplayCheck` независимо проверяет проникновение частиц в чужую живую ткань
на каждом тике и дважды воспроизводит всю запись: сверяет координаты/скорости
каждого тика и скрытое состояние каждые 30 тиков. Старые H выводятся отдельно
и не переписываются; самоповтор новой физики не означает совпадения с прежней.
Эта проверка делает полный перебор и не предназначена для измерения скорости.

## Сравнение версий

`refactorCheck` проверяет исходные хэши журнала и дополнительный неизменяемый снимок
скрытого состояния. `check` никогда не записывает эталон заново.

```text
gradlew :physics-lab:refactorCheck -Plog=<запись> -Pcheckpoint=<эталон> -PperfTicks=1200
gradlew :physics-lab:scaleParityCheck -Pbaseline=<classpath.txt> -Pbody=<тело> -Pcopies=108
```

Для `scaleParityCheck` предпочтителен файл с полным сохранённым classpath прежней
версии, включая отдельные копии JAR ядра и рендера. Пути разделены системным
разделителем classpath (`;` на Windows). Два независимых загрузчика в одном JVM
чередуют старый и новый тик, сверяют биты позиций/скоростей после каждого тика и
измеряют wall/CPU time. Каталог старых классов поддерживается для прежних монолитных
эталонов; при переносах между модулями используйте полный снимок classpath.
Повторите замер в отдельном JVM с `-PscaleOrder=new-first` (по умолчанию `old-first`):
первым загружается и прогревается другой вариант. Одного чередования тиков мало,
чтобы исключить влияние порядка на JIT и расположение массивов. Сохраняйте оба результата.

Одинаковые имена сцен и число частиц ещё не гарантируют одинаковую нагрузку:
сравнивайте тело, команды, настройки и число проходов. Простой перенос файлов не
меняет алгоритм и не должен считаться оптимизацией решателя.

Для замеров без общих профилей JIT и общей кучи используйте два отдельных процесса:

```text
gradlew :physics-lab:writeBenchmarkClasspath
python physics-lab/tools/freeze_classpath.py physics-lab/build/bench/classpath.txt build/bench/baseline
```

Снимок делают **до правки**. Команда копирует классы и JAR, записывает SHA-256 и
отказывается перезаписывать существующий каталог. После правки снова выполните
`writeBenchmarkClasspath`, затем:

```text
python physics-lab/tools/compare_versions.py --baseline build/bench/baseline/classpath.txt --current physics-lab/build/bench/classpath.txt --input <тело> --size 108 --tag world-100k
python physics-lab/tools/compare_versions.py --baseline build/bench/baseline/classpath.txt --current physics-lab/build/bench/classpath.txt --mode replay --input <сохранённая-запись> --size 1200 --warm 2 --blocks 4 --tag player
```

Нужны Python 3 и JDK 21 из `JAVA_HOME`/`PATH` (или `--java`). Дополнительные пакеты
Python не используются. Процессы считают по очереди; порядок меняется каждый блок.
На Windows `--affinity 0x4` закрепляет оба процесса на логическом CPU 2; выберите
свободное физическое ядро своей машины. Без этого параметра размещение выбирает ОС.
Для повторного замера поменяйте первый процесс через `--first new`.

В режиме scale `--size` означает число копий тела, `--warm`/`--block` — тики;
`--gait gait` включает мышцы, `--gait slam` наносит удар после прогрева. Для большого
одиночного графа задайте `--size 1 --jit-body <небольшое-настоящее-тело>`: начальный
прогрев JIT тогда не выполнит 200 тиков на всём большом графе. В режиме replay
`--size` — первые N тиков записи (0 — вся), `--warm`/`--blocks` — число повторов.

Сверяется каждый тик; масштабная сцена дополнительно сравнивает скрытые поля после
каждого блока. Для записи исходные суммы H обязательны, полный скрытый эталон
проверяется отдельно через `refactorCheck`. Хэши и снимки не входят в wall time
физики; CPU time включает сбор хэшей. JSON, вывод процессов и параметры JVM лежат
в `build/reports/isolated-bench` (меняется через `--output`). Результат одного запуска
не исключает влияния фоновой нагрузки, нагрева и размещения данных JVM.

Для изменения численной схемы дополнительно запускайте `materialCheck` на одном
и том же теле с мягкими связями в обеих версиях. Он считает по 600 тиков покоя,
удержания мышцы и гребка на двух копиях тела без свободных частиц. Средняя
невязка связей берётся за последние 480 тиков и делится на среднюю длину связи.
Печатаются также максимум невязки, максимум инверсий, первый тик инверсии/смерти,
число умерших клеток и смещение центра масс в длинах связи. Ввод идентифицируется
CRC; разрыв от растяжения выключен, смерть от глубокого контакта остаётся частью
решателя. Координаты и скорости проверяются на конечность после каждого тика.

Успешное завершение означает сбор метрик, а не одобрение нового материала:
сравните значения обеих версий. Например, вариант 16×1 прошёл `physicsCheck`,
но получил 53 инверсии вместо нуля и был отклонён. Эта диагностика не заменяет
побитовый повтор, проверки столкновений или отдельный замер производительности.
