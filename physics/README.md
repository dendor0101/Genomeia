# Физическое ядро

Новая XPBD-физика, пока без подключения к симуляции игры. Зависимости — только
Kotlin/JDK. В модуле нет окна, libGDX, файлов тела, журналов стенда и настроек процесса.
Текущая реализация ещё однопоточная; выделение модуля не добавляет арены или воркеры.

Принятый режим с 21.10.2026 — 30 UPS, 32 подшага и одна итерация. Внутренние
ограничения обходятся по блокам до 1000 частиц внутри исходного организма:
чётные блоки, нечётные, ограничения через границы, затем общий контактный барьер.
`BlockedIteration` задаёт порядок, `ConstraintBlocks` — принадлежность ограничений,
`DenseBlockIndex` — плотные списки связей/площадей с локальным удалением.
Это подготовка к параллельности: общие очереди разрушения/пределов и обновление
топологии пока требуют последовательного исполнения. Размер 1000 ещё не является
доказанным оптимумом для ПК или телефона. Численные траектории отличаются от 16×4.
После контактов `BoundaryOrientation` проверяет знак площади только у текущего
контура. Это закрывает выворот края внутрь ткани на ручной записи 32×1;
краткие внутренние инверсии и прежнее правило их разрушения сохранены.
Причина, повтор и цена проверки — в [разборе](../docs/physics/contact-orientation-2026-10-21.md).

Каталоги внутри `src/main/kotlin/io/github/some_example_name/physics`:

| Каталог | Что искать |
|---|---|
| `model` | `BodyDefinition`: исходное тело; `BodyState`: рабочие плоские массивы |
| `solver` | `BodySimulation`: load/reset/step и порядок стадий; связи, площади, кости, среда, мышцы |
| `topology` | Исходный граф, компоненты, локальная поверхность, обновление после разрывов |
| `contacts` | Граничные контакты, широкая фаза, CCD, сохранение контактных множителей |
| `damage` | Смерть частиц, пластика и разрушение |
| `config` | Параметры численной модели и неизменяемый снимок настроек запуска |
| `diagnostics` | Необязательные измерения и проверки состояния |

Объявления сохраняют единый пакет `io.github.some_example_name.physics`: разнос
файлов не меняет публичные/JVM-имена уже выделенной библиотеки. Kotlin допускает
такое расположение. Полное переименование в подпакеты дало около 6% потери на 100k
в длинных A/B и отдельном запуске; вариант со старыми именами — около нулевой разницы
CPU. Причина на уровне исполнения JVM не изолирована, поэтому переименование
отброшено, без компенсирующих флагов JVM или изменений численной модели. Замеры
и ограничения — в [отчёте](../docs/physics/modules-2026-10-17.md).

Основной вход — `BodySimulation(BodyState(config))`: `load(definition)`, затем `step()`
и `reset()`. Загрузка выполняется один раз; для другого тела создаётся новое состояние.
`BodyDefinition` после загрузки не изменяется. Настройки передаются значением;
`System.getenv` читает только лаборатория. `StepObserver` нужен для интерполяции окна;
без него ядро не хранит историю кадров.

`BodyState` и отдельные стадии пока доступны инструментам проверки. Это рабочая
граница извлечённого решателя, ещё не стабильный публичный API общего движка.
При введении мира/арен нужно отдельно определить владельца каждого массива, срок
жизни индексов, команды изменений и полный снимок состояния для повторов.

## Проверки

```text
gradlew :physics:test
gradlew :physics-lab:physicsCheck -Pbody=body-export.txt
gradlew :physics-lab:physicsCheck -Pbody=body-export-кирпич.txt
gradlew :physics-lab:playerReplay -Plog=<сохранённая-запись>
gradlew :physics-lab:tissueReplayCheck -Plog=<сохранённая-запись>
```

Повтор считается успешным только после строки «контрольные суммы: все N сошлись».
Запись и соответствующее ей тело нужно сохранять до запуска окна. Остальные
инструменты и способы запуска описаны в [physics-lab](../physics-lab/README.md).
